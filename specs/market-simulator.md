# Market Simulator Contract

The simulator is a deterministic Kraken Spot venue fixture that drives the real
REST and websocket clients. Its primary claim is mechanics correctness: a test
can control the market, transport, execution venue, and exchange-owned account
views without replacing production parsing, routing, or lifecycle code.

It is not evidence of live profitability. Synthetic economics establish only
that the system behaves consistently inside the declared scenario.

## Replay identity

`tests/types.ScenarioConfig` is the complete run identity. A valid scenario
declares:

- a name, scenario seed, and non-zero UTC start time;
- one or more unique symbol profiles;
- the complete latent regime distributions, transition momentum, candle
  interval, and schedule;
- explicit production-book synchronization timeout and polling cadence;
- execution, balance, websocket, and REST timing;
- deterministic order outcomes and transport fault rules;
- optional initial exchange balances;
- the failed-run artifact directory.

Each symbol owns its generator seed, precision, tick size, base spread, fee
tier, finite depth shape, shared-factor loading, and factor lag. The scenario
seed owns the shared factor path and execution outcome path. `FaultConfig.Seed`
owns transport jitter. No wall-clock value enters generated market timestamps:
the default start is the Unix epoch. The same configuration and seeds therefore
produce the same samples and generated bytes.

Invalid, missing, duplicate, non-finite, or unknown configuration is rejected.
The simulator does not silently substitute a symbol, regime, price, fee,
balance, template, or fault action.

## Timeline and scheduling

`Market.Tick` is one synchronous venue step:

1. apply every regime transition scheduled for the current tick;
2. sample one seeded shared market factor;
3. sample each symbol once, in `ScenarioConfig.Symbols` order;
4. publish that symbol's ticker, full L2 book, L3 book, trade, and OHLC views;
5. advance orders and independently timed exchange balance projections;
6. increment the shared tick after every symbol has been processed.

Scheduled transitions do not block and are ordered by their entries in the
scenario. `Transition` and `TransitionAll` are synchronous test controls: they
advance the shared market until the configured observable precursor completes.
`Express` and `ExpressAll` continue until the regime's ignition tail is spent.
The latent regime name is retained only in the test oracle and report; it is
never published to the production stack.

Generated time advances by each active profile's cadence. Symbols therefore
share a tick index but may have different event timestamps. A positive
`FactorLagTicks` reads an earlier shared factor value without changing delivery
order. `PublishSample` preserves an external observation's timestamp and rejects
unknown symbols, stale time, crossed quotes, invalid quantities, inconsistent
cumulative volume, and unordered explicit depth.

When a production `Stack` drives the market, generated timestamps determine
wall-clock pacing. Direct fixture use is synchronous and never sleeps.

## Coherent market views

One `tests/types.Sample` is the source of truth for every channel published for
a symbol step:

- ticker bid, ask, sizes, last, cumulative volume, VWAP, high, and low;
- finite L2 and L3 depth;
- one trade at `Last` for `StepVolume` and `AggressorSide`;
- the current OHLC interval aggregated from those same trades;
- execution eligibility and finite quantities from that same book.

The generator enforces positive prices and quantities, `bid < ask`, price and
quantity precision, ordered depth, and a trade price inside the spread. OHLC
open/high/low/close, trade count, volume, and VWAP are accumulated from the
published trade observations rather than generated independently.

Generated L2 frames are full snapshots. This deliberately prevents stale price
levels from surviving a moved synthetic book. Generated L3 uses a full opening
snapshot followed by ordered delete/add deltas for every stable per-level order
identity. The production L3 reconstruction consumes those deltas before an
execution is evaluated when a driven stack is attached.

Fixture checksums are removed from generated book frames because the simulator
does not claim to implement Kraken's checksum algorithm. Checksum recovery has
dedicated production-book tests and must not be inferred from synthetic values.

## Supported venue events

The fixture boundary supports:

- public ticker, L2 book, trade, OHLC, instrument, and subscription events;
- authenticated L3 snapshots and deltas;
- order acknowledgements and execution events;
- balance snapshots and updates;
- REST Assets, AssetPairs, Time, websocket token, Balance, TradesHistory,
  OpenOrders, CancelOrder, TradeVolume, and AddOrder responses.

Ticker, book, trade, and OHLC do not invent an exchange sequence field because
the corresponding Kraken v2 payloads used by this system do not require one.
Execution and balance events carry monotonically increasing venue sequences.
Every execution also has a unique execution identity. A configured sequence-gap
fault alters a real sequence field; it does not add sequence metadata to a
channel that has none.

`Conn.Publish` is synchronous with the SDK receive callback. Within one
connection, a call returns after the exact frame has been dispatched unless the
configured fault drops it or reconnects the client. No global ordering is
claimed across the public, private, and L3 websocket connections.

## Execution and account semantics

`WithAutoFill` enables the optional stateful execution venue. The default is a
next-sample, top-level, balance-enforced taker fill compatible with the original
fixture. `ExecutionConfig` can instead declare:

- finite executable depth and its quantity curve;
- spread crossing and slippage in basis points;
- execution, acknowledgement, fragment, websocket-balance, and REST-balance
  delays;
- market, limit, stop-loss, and stop-loss-limit behavior;
- seeded partial-fill, rejection, cancellation, no-fill, and limit-fill
  probabilities;
- an exact ordered outcome sequence;
- expiration, maximum order quantity, and balance enforcement;
- execution-before-acknowledgement.

Market orders and triggered stop-loss orders walk the eligible opposite depth.
Limit prices cap the executable levels. A sample cannot supply more quantity
than its declared levels, so a remaining order waits for later replenished
books. This is finite-liquidity consumption for the current observation, not a
full matching engine or persistent exchange queue.

Lifecycle states remain distinct: submitted, acknowledged/open,
partially-filled, filled, canceled, rejected, and expired. An acknowledgement
is never treated as an execution. Executions carry cumulative and last quantity,
cost, average price, cumulative fee, order ID, client ID, execution ID, venue
sequence, and event timestamp.

Exchange balances are checked before every fill. Buys debit quote cost and fee;
sells debit base inventory and credit quote proceeds less fee. Per-symbol maker
or taker fees come from the same profile exposed through REST. Cost basis,
realized gross PnL, fees, slippage, net PnL, fill ratio, and maximum realized
drawdown are reconciled independently of websocket consumers. REST and
websocket balances advance on separate configured clocks.

## Fault model

`FaultConfig` applies exact channel occurrence rules and seeded latency at the
real fixture transport boundary. Supported websocket actions are:

- drop;
- duplicate;
- delay;
- reorder one frame after its successor;
- sequence gap;
- stale replay;
- malformed bytes;
- forced disconnect and SDK reconnect.

Per-channel base latency and bounded seeded jitter apply before delivery.
Per-path REST latency and jitter apply before the fixture response. Rules are
unique by channel and occurrence; ambiguous or impossible rules are rejected.

The transport report stores the exact generated bytes, every delivered byte
sequence, sampled delay, reconnect marker, trigger occurrence, and action. A
dropped, first-occurrence stale, or reconnecting frame remains observable in
the report even though no payload reaches the consumer.

After an L3 disconnect or an unavailable L3 fixture connection, the market
marks local book delivery uninitialized and the next deliverable frame is a
fresh snapshot rather than a delta against missing state.

## Reports, invariants, and failed-run artifacts

`Market.Report` keeps three claims separate:

- transport mechanics for public, private, and L3 connections;
- order mechanics and invariant violations;
- execution economics.

It also records the complete scenario, current tick, latent transition
timeline, and per-symbol regime exposure. `Market.Validate` rejects execution
past ordered quantity, duplicate execution identities, and negative
exchange-side balances. Tests remain responsible for assertions about their
production consumer, including positions, stops, subscriptions, readiness,
and recovery.

`WithScenario` writes a JSON failure artifact containing the scenario, seeds,
timeline, exposure, fault log, exact frames, lifecycles, and economics. Artifact
write errors fail the test rather than hiding the loss of replay evidence.

## Historical replay

`Market.PublishSample` is the ingestion boundary for trade/top-of-book or L2
historical observations after they have been normalized into `Sample`. It
derives the same websocket views and execution behavior as generated data.
Historical prices alone do not establish hypothetical queue position or fill;
the declared `ExecutionConfig` remains the replay fill assumption.

## Intentional limits

The simulator intentionally does not implement:

- a full Kraken matching engine or complete price-time priority;
- undeclared maker queue position beyond the configured limit-fill probability;
- margin, funding, liquidation, or cross-venue mechanics;
- an agent population or adaptive market response to the strategy;
- Kraken book checksum generation;
- historical-distribution calibration without supplied reference data;
- proof that a synthetic regime is representative or profitable live.

Queue fidelity, conditional post-fill market response, distribution
calibration, and historical scorecards belong in a separate calibrated layer
when actual reference data and a concrete validation need are available. Until
then, adding constants for those effects would create performative realism.

## Test standard

Simulator tests should be adversarial, multi-step, and exact. A green result
must prove a named contract or invariant, not merely that a value is non-zero.
Use multiple seeds or metamorphic comparisons for stochastic behavior. In
particular, increased fees, slippage, latency, spread, or order size must not
paradoxically improve the corresponding modeled economics.
